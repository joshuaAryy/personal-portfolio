## Expense rules and anomaly workflow

- **Inputs and rule configuration:** The front-end policy configuration is a local `PolicyConfig` applied to the challenge transaction set. It includes an approval threshold, solo-meal limit, department budgets, per-category limits, allowed categories, restricted merchants, and receipt threshold in [`policy.ts`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/data/policy.ts#L18-L35). Defaults are derived from the bundled transaction data; category caps use a percentile and department budgets derive from mean monthly spend at [`policy.ts`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/data/policy.ts#L49-L92).
- **Deterministic review findings:** `policyViolations()` evaluates debit transactions against configured restricted merchants, allowed categories, caps, meal limits, approval/receipt thresholds, and split transactions in [`intelligence.ts`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/data/intelligence.ts#L74-L169). One supported explanation is: group same employee + merchant + day, check whether multiple charges each fall below the approval threshold while their sum reaches it, and surface a split-transaction review flag. That is a rule-based alert, not proof of intent or misconduct.
- **Anomaly cues:** `anomalies()` derives cues from transaction history. For example, duplicate checks group exact employee/merchant/amount matches and flag pairs within three days; other code computes employee/category baselines and daily spend totals ([`intelligence.ts`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/data/intelligence.ts#L367-L445)). Treat these as deterministic demo heuristics for human investigation, consistent with `CASE_STUDY_CONTENT_SOURCE.md`; do not present them as ML fraud classification.
- **Interpretation boundary:** These mechanics show how rule thresholds and transaction patterns yield review signals. The actual front-end uses local/configured challenge data, and some display-oriented conditions use stable ID hashes to populate threshold/receipt flags. This repository therefore supports an explanatory challenge-workflow story, not customer policy outcomes or production fraud performance.

## Preapproval and human decision

- The queue is built from a small set of hard-coded `REQUEST_TEMPLATES`; `approvalQueue()` combines a template with selected employees, transaction history, budget configuration, and prior similar charges, then derives a budget-based approve/deny/review fallback ([`intelligence.ts`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/data/intelligence.ts#L861-L958)). The function is explicitly named a mock queue in source. Its sample requests are not actual customer activity.
- `ApprovalsView` submits request context—employee, department, amount, category, merchant, remaining budget, and history—to a Gemini approval-recommendation route. The AI response can replace the template recommendation in the view; otherwise the template fallback is shown ([`ApprovalsView.tsx`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/views/ApprovalsView.tsx#L29-L76)). The Python route packages the request and history with an expense-data summary and calls Gemini ([`approvals_ai.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/routers/approvals_ai.py#L41-L82)).
- A person still chooses Approve or Deny. In this UI those actions update React state and a local past-decisions list; they do not demonstrate a connected external approval system ([`ApprovalsView.tsx`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/views/ApprovalsView.tsx#L193-L233)).
- **Copy boundary:** Source truth verifies Joshua contributed to part of preapproval, but this source inspection does not attribute the queue, rule formula, Gemini integration, UI, or state handling to him individually. Public copy should keep his scope at “part of the preapproval workflow” unless another artifact verifies more.

## Policy-PDF retrieval path

The repository contains a separate Node.js policy-RAG prototype in `retrievelogic/`; it is distinct from the main expense review UI and from generic FastAPI file-Q&A routes.

1. [`ingest.js`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/retrievelogic/ingest.js#L79-L113) locates a Brim expense policy PDF, extracts its text, splits it into 700–1,200 character pieces (minimum 80 characters), calls Gemini embeddings, and stores text + vectors + source metadata in MongoDB collection `policy_chunks`. The script defaults to `gemini-embedding-001` and 3,072 dimensions, replaces prior chunks for the same source file, and tells the operator to create the Atlas vector index.
2. [`mainlogic.js`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/retrievelogic/mainlogic.js#L67-L96) embeds the policy question and runs Atlas `$vectorSearch` against `policy_chunks` with `numCandidates: 100` and `limit: 5`.
3. It passes retrieved text to a separate Gemini chat model with a prompt to use only those policy passages, avoid inventing policy rules, and say when context is insufficient; the return includes the retrieved sources ([`mainlogic.js`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/retrievelogic/mainlogic.js#L98-L128)).

This code materially corroborates the reported **PDF extraction/chunking → embedding → Atlas `policy_chunks` → vector retrieval → grounded interpretation** design. Small naming detail: committed defaults say `gemini-embedding-001`, while the portfolio source record names `embedding-001`. Keep the public label aligned with the owner-approved record unless the model name is deliberately reconciled. The files are standalone Node scripts/CLI, not evidence of a production endpoint or successful live deployment. The source tree’s generic `/ingest` and `/query` API is a separate flow: it keeps uploaded text/chunks in process memory and the query route sends only the first chunk to Gemini ([`ingest.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/routers/ingest.py#L37-L72), [`query.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/routers/query.py#L14-L39), [`main.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/main.py#L22-L34)). Do not merge that generic route with policy vector search.

## Finance Q&A / reporting is separate

- The browser Ask implementation builds a compact summary from the bundled transaction/employee data, asks Gemini for an answer, and exposes local functions the model may call to look up employee, transaction, department, category, or vendor details. Calls are proxied through the serverless `/api/gemini` handler so the API key stays server-side ([`ai.ts`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/frontend/src/data/ai.ts#L478-L550), [`api/gemini.js`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/api/gemini.js#L1-L49)).
- A parallel FastAPI `/api/ask` path reads employees and the `transactions_clean` Mongo collection, maps fields into a compact aggregate summary, caches it for 60 seconds, and sends it with conversation history to Gemini. The response includes text, chart type/data, and follow-up questions ([`ask.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/routers/ask.py#L40-L69), [`ask.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/routers/ask.py#L119-L165), [`gemini.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/services/gemini.py#L199-L226), [`gemini.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/services/gemini.py#L382-L410)).
- The repo also has a separate `/api/policy/analyze` endpoint that summarizes submitted violation records with the expense-data summary; it is not the PDF vector-retrieval path ([`policy_ai.py`](https://github.com/Atlearia/mpchacks/blob/32d4dc19ea95fe1ba795613f7681fcf353947565/app/routers/policy_ai.py#L46-L75)).

**Public-story consequence:** It is safe to show Finance Q&A/reporting as a separate workspace capability and describe the checked code as transaction-data summary + conversational Gemini/chart output. ## Evidence-backed story implications

- A deeper Crest explanation can use: request context → editable deterministic rules/heuristic cues → policy-PDF retrieval prototype → separate finance-question/reporting path → human-selected action.
- Use one verified code example for split transactions, duplicate heuristics, or a rule/cap explanation; use no invented transaction values. If the UI values appear, label them challenge/sample data.
- Keep the answer and decision boundaries clear: finance/policy rules and heuristics are review support; Gemini interprets supplied policy text or offers a preapproval recommendation; a reviewer makes the final decision in the demo.
- The repo corroborates technical structure, not Joshua’s finer ownership, customer impact, or production deployment. Source-authoritative ownership remains limited to the areas listed in `docs/CASE_STUDY_CONTENT_SOURCE.md`.
